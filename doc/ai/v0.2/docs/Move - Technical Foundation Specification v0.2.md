## 0. Starting point and reuse mode

A complete operational Rails shell application will be provided. It is generated by a Rails application template and already includes the deployment path, CI/CD workflow, authentication layer, baseline test/lint tooling, and production wiring.

This specification is therefore **not** a command to rebuild the whole foundation from scratch.

Implementation begins with a foundation audit:

1. Confirm what the shell already provides.
2. Compare it against this specification.
3. Implement only the missing deltas needed for Move.
4. Preserve working deployment, authentication, CI, and workflow behavior.

The previous `catalyst` application remains a production-derived reference for conventions and target architecture, not a source for file-for-file copying.

## 1. Product-specific technical decisions

The following decisions override earlier drafts where they conflict.

| Area | Decision |
|------|----------|
| Tenancy | Subdomain tenancy, row-level shared schema, global user identity. |
| Account model | Organization owns Moves. Organization is resolved from subdomain. |
| Move access | MoveMembership controls Move permissions with roles `admin`, `contributor`, `viewer`. |
| Organization membership | OrganizationMembership grants account presence. It is not a product-facing Move role. |
| Offline | No offline domain mutations in Phase 1. PWA shell may exist, but capture/edit require connectivity. |
| Recognition | Provider-agnostic adapter, image-only Phase 1, RecognitionRun + RecognitionSuggestion. |
| Recognition storage | No vendor-specific schema leakage into domain tables. Do not persist raw provider responses in domain tables. |
| Bounding boxes | Not supported. No crop coordinates, crop previews, or highlighted source regions. |
| Search | Hybrid PostgreSQL: full-text + `pg_trgm` + `pgvector`. |
| Measurements | Use canonical measurement storage and display conversion. Shopify `measured` can be used for dimensions/weight. |
| Restore | Restore cascades to children discarded by the same parent delete action, without resurrecting previously deleted children. |
| MCP | Revocable per-Move integration tokens. Tokens may mutate through shared domain actions. |
| Media | Retain source media indefinitely. No crop variants required. |
| UI strings | Phase 1 is English-only, but all customer/UI-facing strings must live in Rails I18n YAML files. |

## 3. Architectural principles

- **Thin controllers, fat Actions.** All writes go through actions. Controllers parse params, call actions, authorize, and render.
- **Events for side effects.** Meaningful mutations emit `Rails.event.notify(...)`. Audit, notifications, and broadcasts are subscribers.
- **Tenant isolation everywhere.** Collection reads use ActionPolicy relation scopes. No manual controller scoping as the only protection.
- **Shared core logic.** Web UI and MCP tools call the same actions.
- **Soft delete by default.** User-authored domain records are discarded, not destroyed.
- **Restore must be deliberate.** Cascaded restore uses a trace of which children were discarded by the same parent deletion.
- **No offline queue.** Service workers may cache shell assets, but not domain mutations.
- **No crop pipeline.** Do not generate or persist image crops for item review.
- **Provider boundaries.** Recognition and embeddings are behind interfaces so vendors can change without domain rewrites.
- **I18n string discipline.** Phase 1 ships English only, but customer/UI-facing copy is never hard-coded. Store it in YAML locale files and render through Rails I18n.
- **Pack boundaries.** Domain slices may live under packs if the shell uses Packwerk.

## 4. Tenancy model

### 4.1 Isolation strategy

Use row-level, shared-schema tenancy.

- One PostgreSQL cluster and app schema.
- Tenant-owned tables carry `organization_id uuid NOT NULL`.
- Most Move-owned tables also carry `move_id uuid NOT NULL`.
- Composite indexes enforce tenant-scoped uniqueness.
- Cross-tenant access returns 404 when existence disclosure matters.

### 4.2 Subdomain resolution

Subdomain tenancy is chosen.

Example:

```text
john.moving.example
```

Resolution rules:

1. Extract organization slug from subdomain.
2. Find Organization by slug.
3. Set `Current.organization`.
4. Find `Current.organization_membership` for the authenticated user.
5. Deny with non-disclosing response if no membership.

Local dev should support a wildcard pattern such as:

```text
https://john.<APP>.<DOMAIN>.docker
```

### 4.3 Models

#### Organization

- `name`
- `slug`, unique globally
- `settings` jsonb
- `created_by_user_id`

#### OrganizationMembership

- `organization_id`
- `user_id`
- `account_admin` boolean, default false
- unique `(organization_id, user_id)`

OrganizationMembership is only the account gate. Move permissions are never inferred from a product-facing org role.

#### MoveMembership

- `organization_id`
- `move_id`
- `user_id`
- `role` enum: `admin`, `contributor`, `viewer`
- unique `(move_id, user_id)`

A user must have OrganizationMembership before MoveMembership.

### 4.4 Current context

`Current` carries:

- `actor` - User or system actor
- `organization`
- `organization_membership`
- `move` when a route/tool is Move-scoped
- `move_membership` when a route/tool is Move-scoped
- `source` - `web`, `mcp`, or `system`
- `request_id`

Background jobs and MCP tools must restore all required Current fields from explicit arguments. Never rely on request Current across enqueue boundaries.

### 4.5 Invitations

- Organization invitations create/link user and OrganizationMembership.
- Move invitations require or create OrganizationMembership first, then create MoveMembership.
- Move invite role choices are admin, contributor, viewer.
- Signup forms must carry invite tokens through hidden fields when Rodauth POSTs drop query params.

## 5. Authorization

Use ActionPolicy.

### 5.1 Context

Policies receive user, organization, and move context where applicable.

Base helpers:

- `account_admin?`
- `move_admin?`
- `move_contributor?`
- `move_viewer?`
- `move_writable?` meaning admin or contributor and Move not archived.
- `superadmin?` for operators, kept outside organization and move roles.

### 5.2 Relation scoping

Every policy for tenant data defines relation scope, typically:

```ruby
relation_scope do |relation|
  relation.where(organization: authorization_context[:organization])
end
```

Move-owned resources additionally scope by authorized MoveMembership when needed.

Controllers use `authorized_scope(Model.all)` for collections.

### 5.3 Rule idioms

- Read: any MoveMembership role.
- Mutate inventory: admin/contributor and Move not archived.
- Manage members: admin only.
- Manage categories/tags/rooms: admin only.
- Manage integration tokens: admin only.
- Restore: mirrors delete permission plus state rules.
- Sensitive content read such as manifests: any Move member, auth-gated, optionally audited.

## 6. Domain model implementation notes

### 6.1 Tables

Required Phase 1 domain tables:

- organizations
- organization_memberships
- moves
- move_memberships
- rooms
- categories
- tags
- box_tags or taggings
- item_tags or taggings
- boxes
- media
- recognition_runs
- recognition_suggestions
- items
- move_integration_tokens
- item_search_documents or equivalent search projection

Use `organization_id` on each tenant-owned table, including Move-owned tables, for direct scoping and indexing.

### 6.2 Measurements

Use canonical storage, not display-unit storage.

The UI displays based on Move unit system, but changing unit system does not reinterpret stored values.

Suggested shape:

- Store length/width/height in a canonical unit such as millimeters or centimeters.
- Store weight in a canonical unit such as grams or kilograms.
- Use a measurement abstraction to parse/display metric and imperial values.
- Derived volume is calculated, not stored as source-of-truth.

Shopify `measured` may be used for conversion and Active Record integration.

### 6.3 No bounding boxes

Do not create columns named `bounding_box`, `source_frame_ref`, `crop`, or similar for Phase 1.

If a recognition provider returns bounding boxes, the adapter discards them before creating domain records.

### 6.4 Category and tag data

Category is singular and belongs to an item through `category_id`.

Tags are optional and many-to-many.

Both are controlled vocabularies scoped to Move. No free-text values from item/box forms.

Every mutating action should:

1. Authorize up front.

5. Emit a structured domain event.
6. Return `Success(record_or_result)` or `Failure(errors_or_symbol)`.

## 8. Events, audit, and concurrency

### 8.1 Event conventions

Payloads include:

- `organization_id`
- `move_id` when applicable
- `actor_id`
- `source`
- primary record id
- parent ids needed after discard
- changes for updates
- from/to state for transitions

Examples:

```text
move.created
box.created
box.status_changed
media.captured
recognition_run.queued
recognition_run.failed
recognition_suggestion.accepted
item.updated
item.moved
item.removed
tag.renamed
room.removed
manifest.generated
move_integration_token.revoked
```

### 8.2 Activity feed

The audit log remains append-only.

Activity feed records ordinary concurrent edits. Last action wins, but prior actions are visible and restore/revert may be available where safe.

### 8.3 Conflict behavior

Server validations handle stale UI.

Recognition conflicts use an explicit state rather than silent overwrite:

- If a user confirmed or edited an item after a recognition run started, later suggestions from that run must not overwrite it.
- The implementation may mark the suggestion `conflict` or the item `needs_correction`.
- UI presents a human resolution path.

## 9. Soft delete and cascade restore

The original parent-only restore rule is not valid for Move.

Move requires cascade restore for children discarded by the same parent delete action.

### 9.1 Required behavior

- Deleting a parent soft-deletes its dependent children.
- Restoring that parent restores children that were discarded by the same cascade delete action.
- Children discarded earlier for independent reasons stay discarded.

### 9.2 Implementation approach

Add an explicit cascade trace, for example:

- `discarded_at`
- `discarded_by_parent_type`
- `discarded_by_parent_id`
- `discard_cascade_root_id` or `discard_batch_id`

A delete action generates one batch id and applies it to records discarded by that action.

A restore action restores records with the same batch id and parent/root relationship.

Do not rely only on callbacks if they cannot express the restore graph safely.

### 9.3 Tests

Tests must cover:

- parent delete discards children;
- parent restore restores cascade-deleted children;
- parent restore does not restore children independently discarded before parent delete;
- authorization still applies to restore.

## 10. Recognition pipeline

### 10.1 Architecture

Recognition is behind an adapter interface.

```ruby
module RecognitionProviders
  DetectedObject = Data.define(:label, :confidence, :count)
  Result = Data.define(:provider, :provider_model, :objects)

  class Base
    def identify(image:, context:)
      # returns RecognitionProviders::Result
    end
  end
end
```

The normalized minimum result shape is intentionally compatible with the `identify_objects.rb` prototype:

```json
[
  {"label":"coffee machine","confidence":0.98,"count":1},
  {"label":"fruit","confidence":0.93,"count":3}
]
```

OpenAI and Anthropic adapters may produce different labels and granularity for the same image. For example, one adapter may return `bag`; another may return `protein powder bag (Myprotein Impact Whey Isolate)`. Both are valid if they normalize into `label`, `confidence`, and `count`. The richer label should be preserved as the proposed item name.

Phase 1 should include:

- A fake/stub provider for tests and local deterministic development.
- Production adapter classes for configured providers, initially shaped around the OpenAI/Anthropic command-line prototype.
- Provider selection via environment/configuration, for example `RECOGNITION_PROVIDER=openai|anthropic|fake`.
- A normalized result object independent of vendor schema.

### 10.2 Processing flow

1. Admin/contributor captures image to Box.
2. Media is created after upload succeeds.
3. RecognitionRun is created with `queued`.
4. Solid Queue job restores Current context and marks run `processing`.
5. Provider returns normalized suggestions.
6. Suggestions are persisted.
7. Auto-confirm threshold determines auto-confirmed vs pending review.
8. Run becomes succeeded, partially succeeded, or failed.
9. Search indexing jobs enqueue for confirmed items.

### 10.3 Failure and retry

- Failure stores sanitized code/message.
- Retry creates a new RecognitionRun.
- Manual item creation remains available.
- Provider timeouts and invalid responses must not leave runs stuck in `processing`.

### 10.4 No vendor leakage

Do not store raw provider response in domain tables.

Allowed metadata is provider-independent and operational, such as:

- item count returned;
- duration;
- sanitized error category;
- provider adapter version;
- provider name and model label.

Adapter responsibilities:

- Convert the image blob to the provider-required media representation.
- Send a strict JSON prompt requesting only an array of objects with `label`, `confidence`, and `count`.
- Parse and validate the returned JSON.
- Clamp or reject malformed confidence/count values.
- Return normalized `DetectedObject` records.
- Convert invalid JSON, timeout, or provider API errors into failed RecognitionRuns with sanitized errors.

Adapters must not persist raw provider responses or vendor-specific payload structures in domain tables.

## 11. Hybrid search

### 11.1 PostgreSQL extensions

Enable:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS vector;
```

### 11.2 Search projection

Use a projection such as `item_search_documents` or equivalent materialized fields.

Suggested fields:

- `organization_id`
- `move_id`
- `item_id`
- `search_text`
- `search_tsvector`
- `embedding vector(n)`
- `embedding_model`
- `embedding_updated_at`

### 11.3 Indexing

- GIN index for full-text vector.
- GIN or GiST trigram index for fuzzy search.
- HNSW pgvector index when supported and dataset warrants it; IVFFlat is acceptable if HNSW is not suitable.
- Composite tenant filters such as `(organization_id, move_id)`.

### 11.4 Querying

Search action:

1. Authorize Move access.
2. Filter by `organization_id` and `move_id`.
3. Compute lexical rank.
4. Compute trigram similarity.
5. Compute query embedding if configured.
6. Combine scores with lexical exact-match boosts.
7. Return item, box number, room, and match explanation fields.

### 11.5 Fallback

If embedding generation is unavailable or not yet complete, lexical + trigram search remains functional.

Because recognition is part of Phase 1, the target Phase 1 product should ship hybrid search rather than lexical-only, unless recognition is explicitly stubbed by a later product decision.

## 13. Object storage

- Use Active Storage with the shell's configured S3-compatible service.
- Prefix object keys or otherwise attribute blobs by organization.
- Enforce authorization on blob access paths.
- Retain source media indefinitely.
- Do not generate crop variants for item review.
- Thumbnails for media gallery are allowed as generic media previews, not item crops.

## 14. MCP framework

### 14.1 Auth

Replace org-wide static API key assumptions with MoveIntegrationToken resolution.

Bearer token flow:

1. Hash provided token and find active MoveIntegrationToken.
2. Resolve Move and Organization.
3. Set `Current.organization`, `Current.move`, `Current.source = :mcp`.
4. Set actor identity to an integration/system actor or owning user representation suitable for audit.
5. Enforce token not revoked.

### 14.2 Tools

Initial tools call shared domain actions:

- `search_items`
- `get_box_contents`
- `list_boxes`
- `add_item_to_box`
- `add_media_to_box`
- `move_item`
- `mark_unpacked`
- `get_volume_summary`

### 14.3 Permissions

Tokens may mutate data in Phase 1, but all mutations still flow through actions and authorization-equivalent guards.

### 14.4 Audit

Audit records source `mcp`, token id/name where safe, and affected Move/record ids.

Messaging channels are out of scope.
