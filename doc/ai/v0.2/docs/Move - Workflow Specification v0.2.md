# Move - Workflow Specification

**Version:** 0.2.2
**Status:** Process and governance source of truth for Move implementation
**Pairs with:** Design, Domain, Technical Foundation, and phase files under `prompts/`

---

## 0. Version 0.2 changes

- The app starts from an operational Rails shell generated by the base template.
- Phase 00 is an audit/alignment phase, not a rebuild.
- Each numbered implementation phase has its own Markdown file under `prompts/`.
- Subdomain tenancy is a required runtime verification path.
- No offline capture/edit verification is required in Phase 1.
- Recognition, hybrid search, MCP Move tokens, and cascade restore are explicit verification targets.
- Customer/UI-facing strings must be checked for YAML I18n usage in every phase.
- The agent never merges PRs and never releases before human merge.

---

## 1. Principles

- **Issue first, always.** No code without a tracked GitHub issue.
- **One concern per branch, one logical change per commit.** Small, atomic, reversible.
- **The pipeline is the contract.** Lint, tests, system tests, runtime verification, PR, review, merge, release.
- **`main` is always releasable.** Protected and updated only by reviewed PRs merged by a human.
- **Quality gates are not optional.** Fix failures; do not bypass gates.
- **Verify behavior, not just rendering.** A page that renders is not a feature that works.
- **Respect the shell.** Do not rebuild working foundation unless Phase 00 proves a required capability is missing.
- **Respect the phase file.** Each phase must stay within its own scope unless the PR explicitly documents a safe adjustment.
- **I18n from the start.** Phase 1 is English-only, but customer/UI-facing strings belong in YAML locale files and must not be hard-coded in views, components, controllers, mailers, or notifications.

## 3. Branch strategy

GitHub Flow:

```text
main (protected) <- PR <- feature/*
```

Branch from the latest `main`.

| Prefix | Use |
|--------|-----|
| `feature/*` | new functionality |
| `fix/*` | bug fixes |
| `refactor/*` | internal restructuring, no behavior change |
| `docs/*` | documentation only |
| `test/*` | tests only |
| `chore/*` | tooling, dependencies, housekeeping |

Daily loop:

```bash
git checkout main
git pull
git checkout -b feature/phase-n-short-name
```

## 4. Phase lifecycle

For each phase:

1. Read the current Design, Domain, Technical Foundation, Workflow, and the phase file.
2. Create a GitHub issue using the phase file as the plan.
3. Add the issue to Backlog.
4. Confirm labels exist with `gh label list`.
5. Label and assign the issue.
6. Move it to Ready.
7. Move it to In Progress when work starts.
8. Create a branch.
9. Implement with atomic commits.
10. Run pre-commit validation.
11. Run runtime verification relevant to the phase.
12. Push and open PR.
13. Move issue to In Review.
14. Respond to every review comment and resolve every thread.
15. After human rebase-and-merge, confirm main CI/deploy state.
16. Publish a SemVer `vX.Y.Z` release (per `AGENTS.md` Release Rules) if the phase is releaseable.
17. Record issue, PR, verification, and release URL in the phase file.
18. Move issue to Done.

Board flow:

```text
Backlog -> Ready -> In Progress -> In Review -> Done
```

## 5. Commit conventions

Format:

```text
<type>(<scope>): <subject>

<body>

<footer>
```

Types:

- `feat`
- `fix`
- `docs`
- `style`
- `refactor`
- `test`
- `chore`

Rules:

- Subject is imperative and concise.
- No trailing period.
- Keep subject around 60 characters or less when possible.
- Body explains what and why.
- Reference the issue with `Refs #N` or `Closes #N`.
- Never include AI authorship or generated-by lines.
- Prefer many small, focused commits over one giant commit.

## 6. Pre-commit validation

Run in order before committing or before final push if the shell's hooks already run per commit:

```bash
bundle exec rake project:fix-lint
bundle exec rake project:lint
bundle exec rake project:tests
bundle exec rake project:system-tests
bin/brakeman
bundle exec bundler-audit check --update
```

If the shell uses `mise`, prefix commands when needed:

```bash
mise x -- bundle exec rake project:tests
```

Build fixtures with FactoryBot. Do not use raw `Model.create!` in tests where factories encode required associations.

---

## 7. Overcommit hooks

Resolve hook failures instead of bypassing.

- Pre-commit: trailing whitespace, FIXME/TODO token check, RuboCop.
- Commit-msg: subject formatting and width.
- Do not disable overcommit wholesale.
- For a genuine false positive, skip only the specific hook and document why in the commit body.

## 8. Environment and tooling

- Use `unset GITHUB_TOKEN` before `gh` commands if stale env tokens cause auth problems.
- Use `mise x -- <cmd>` when the shell is not already activated.
- Use local subdomain URLs for tenant verification:

```text
https://john.<APP>.<DOMAIN>.docker
https://acme.<APP>.<DOMAIN>.docker
```

- Use current documentation lookup tools available in the environment.
- Use live browser verification tools available in the environment.
- When using `docker exec` with `bin/rails runner`, avoid shell issues with Ruby bang methods by using heredoc files.

## 9. Runtime verification

Runtime verification is mandatory before push/PR for implementation phases.

### 9.1 Base steps

```bash
bin/cli app rebuild
bin/cli services start
bin/cli mail start
```

Verify:

- app health check passes;
- PostgreSQL and Solid databases exist;
- storage service is reachable;
- mail catcher receives mail;
- app renders logged out and logged in.

### 9.2 Core checklist

Adapt per phase, but do not skip relevant items.

- [ ] Passwordless auth works: invitation, sign-up, magic link, passkey, optional Google, sign-out, remember-me.
- [ ] Subdomain tenancy works: each Organization resolves by subdomain.
- [ ] Cross-org access returns 404 or non-disclosing failure.
- [ ] Move creation creates creator MoveMembership admin.
- [ ] Move roles work: admin, contributor, viewer.
- [ ] Archived Move is read-only.
- [ ] Boxes CRUD works within Move scope.
- [ ] Box number auto-generation and uniqueness work.
- [ ] Controlled vocabularies work: rooms, categories, tags.
- [ ] Image capture uploads media and queues recognition.
- [ ] Recognition states are visible: queued, processing, succeeded, failed/retry.
- [ ] Review flow works: keep, correct, false detection.
- [ ] Recognition never overwrites a user-confirmed item silently.
- [ ] Search works using lexical/fuzzy and semantic matching when configured.
- [ ] QR scan is auth-gated and does not change box status.
- [ ] Exterior label contains no contents.
- [ ] Manifest is authenticated and warns about sensitive contents.
- [ ] Unpacking can mark items removed and restore them.
- [ ] Marking box unpacked marks all in-box items removed.
- [ ] Cascade restore restores children from the same delete batch only.
- [ ] MCP Move token can be created, used, and revoked.
- [ ] Audit log records meaningful mutations.
- [ ] Notifications/push work where the phase touches those paths.
- [ ] Dark mode and flash/toast states remain readable.
- [ ] No runtime errors on any page.

### 9.3 Server-side checks

When verifying actions, jobs, MCP tools, or subscribers with `bin/rails runner`:

- build fixtures with FactoryBot;
- set `Current.actor`, `Current.organization`, and `Current.move` explicitly;
- do not assume request Current exists in jobs or runner contexts.

## 10. Pull requests

Open PRs with `gh pr create` after pushing.

PR description must include:

- what changed;
- why it changed;
- how it was verified: lint, tests, system tests, runtime checks;
- what is out of scope;
- issue link, usually `Closes #N`.

The agent does not merge.

---

## 11. PR review response rules

When review comments arrive:

1. Read all comments.
2. Evaluate each: fix, explain, or defer.
3. For fixes, commit and push, then reply naming the fix.
4. For incorrect comments, reply with technical explanation.
5. For deferred comments, state the future phase or issue.
6. Reply to every comment.
7. Resolve every conversation.
8. Never leave review threads unanswered.

---

## 12. Release rules

Release runs only after the PR has been rebase-and-merged to `main` by a human.

1. Sync local main.
2. Confirm merge commit is present.
3. Confirm main CI/deploy is green or that deploy was intentionally skipped for docs-only changes.
4. If this is a releaseable implementation phase, create a SemVer release tag
   (`vMAJOR.MINOR.PATCH`, optionally with a `-<domain-slug>` suffix so the tag
   names the domain — e.g. `v0.7.0-boxes-home`; the `v*` prefix keeps the
   release bug scan running):

```bash
unset GITHUB_TOKEN && gh release create vX.Y.Z \
  --repo <OWNER>/<REPO> \
  --target main \
  --title "vX.Y.Z - <short title>" \
  --generate-notes
```

5. If that tag already exists, stop. Do not overwrite.
6. Record release URL in the phase file.
7. Move issue to Done.

Tags do not trigger deploy unless the repository explicitly changes that behavior.

## 13. CI/CD behavior

- CI runs on PRs and pushes to main.
- CI should include lint, Packwerk if present, Brakeman, bundler-audit, RSpec, and system tests.
- Do not use `[skip ci]`.
- Docs-only deploy avoidance should use `[skip deploy]` if the repo supports it.
- Keep protected main and human merge rules intact.

---

## 14. Engineering guardrails

- Rails.event subscribers implement `#emit(event)`, not `#call`, if the shell uses Rails structured events.
- Subscriber errors must never break user actions.
- Rodauth forms lose query parameters on POST; carry tokens through hidden fields.
- Pre-fill forms from trusted context instead of asking users to retype known values.
- Render Phlex components in Turbo Streams with `layout: false`.
- Tailwind class changes require CSS rebuild.
- Jobs/runners do not inherit Current.
- Do not add offline mutation queues in Phase 1.
- Do not add bounding-box or crop UI/data.
- Do not introduce Move roles other than admin, contributor, viewer.
- Do not expose raw recognition provider responses as domain data.
- Do not create org-wide MCP tokens; use per-Move integration tokens.

---

## 15. Definition of Done

A change is Done only when all hold:

- [ ] Tracked issue moved to Done.
- [ ] Work stayed within the phase scope or documented safe adjustments.
- [ ] Atomic commits with conventional messages.
- [ ] No AI attribution in commits.
- [ ] Lint clean.
- [ ] Tests green.
- [ ] System tests green.
- [ ] Brakeman and bundler-audit clean or documented accepted findings.
- [ ] Runtime verification performed.
- [ ] PR opened with verification notes.
- [ ] Every review comment answered and resolved.
- [ ] Human merged to main.
- [ ] Main CI/deploy checked.
- [ ] Numbered phase release created if applicable.
- [ ] Phase file updated with issue, PR, verification, and release notes.
